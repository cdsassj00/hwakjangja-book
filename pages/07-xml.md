# 07. XML — 당신의 세금계산서도 이 형식입니다

거래처에서 세금계산서를 보내왔습니다. 그런데 첨부파일이 PDF도 이미지도 아닌 `20260808_1234.xml`입니다. 더블클릭하면 열리지 않거나, 열려도 꺾쇠괄호가 빽빽한 화면이 나옵니다. 회계 담당자는 이것을 어떻게 해야 할지 몰라 다시 보내 달라고 연락합니다.

그런데 그 파일이 정본입니다. 우리나라 전자세금계산서는 **법으로 정해진 XML 파일 자체를 주고받도록** 되어 있습니다. 메일로 전달할 때도 XML 파일을 보내야 합니다. 흔히 보는 PDF나 화면 출력물은 사람이 읽으라고 만든 사본이고, 세무 자료로서 효력을 갖는 원본은 그 낯선 파일 쪽입니다.

그리고 사실 여러분은 이 형식을 이미 여러 번 만났습니다. 이 책의 1장에서 한글 문서를 열었을 때 나온 `<hp:t>`, 2장의 워드에서 본 `<w:t>`, 파워포인트의 `<a:t>`, 4장에서 메모장으로 그림을 그릴 때 쓴 `<circle>`이 전부 XML입니다. 여섯 장에 걸쳐 계속 마주쳤던 그것을 이제 정면으로 봅니다.

## 무엇으로 열고, 무엇으로 고치나

여는 도구는 이번에도 **브라우저**입니다. 그런데 이번에는 앞 장의 JSON보다 훨씬 잘해 줍니다.

`.xml` 파일을 크롬 창에 끌어다 놓으면 내용을 계층 구조로 정리해 보여 줍니다. 제가 직접 열어 보니 맨 위에 "이 XML 파일에는 스타일 정보가 없어서 문서 구조를 아래에 표시한다"는 안내가 뜨고, 그 아래에 이름표들이 들여쓰기된 나무 모양으로 펼쳐졌습니다. 항목 앞의 삼각형을 눌러 접었다 펼 수도 있습니다. 세금계산서 XML을 받았을 때 안을 확인하려면 이것으로 충분합니다.

더 반가운 것은 브라우저가 **잘못된 곳을 잡아 준다**는 점입니다. 일부러 태그 하나를 잘못 닫아 열어 보니 "2번째 줄 34번째 칸에서 여는 태그와 닫는 태그가 맞지 않습니다"라는 오류를 정확히 짚어 주었습니다. 앞 장에서 JSON은 잘못돼도 아무 말 없이 그냥 보여 주기만 했지요. 이 차이는 실무에서 꽤 큽니다. 브라우저 하나가 곧 검사기 노릇을 하기 때문입니다.

고치는 일은 **메모장**으로도 되고, 파일이 크고 복잡하다면 **VS 코드**가 편합니다. 다만 세금계산서처럼 법적 효력이 있는 문서는 열어서 확인만 하시고 내용을 고치지는 마십시오. 원본을 손대는 것은 확인의 범위를 넘어서는 일입니다.

## 이름표로 감싼다는 것

XML은 Extensible Markup Language의 줄임말입니다. 우리말로 옮기면 "확장할 수 있는 표시 언어"쯤 되는데, 이름보다 하는 일이 훨씬 단순합니다. **글자를 이름표로 감싸는 것**이 전부입니다.

```text
<직원>
  <이름>홍길동</이름>
  <부서>영업1팀</부서>
  <사번>00123</사번>
</직원>
```

`<이름>`으로 열고 `</이름>`으로 닫습니다. 닫는 표에는 빗금이 붙습니다. 이 규칙 하나만 알면 세상의 모든 XML을 읽을 수 있습니다. 사람이 봐도 무슨 뜻인지 짐작이 가고, 프로그램은 이름표를 보고 필요한 자리를 정확히 찾아냅니다.

앞 장의 JSON과 하는 일이 같아 보이실 겁니다. 실제로 같습니다. 다만 성격이 다릅니다.

| | XML | JSON |
|---|---|---|
| 적는 법 | `<이름>홍길동</이름>` | `"이름": "홍길동"` |
| 같은 내용의 길이 | 길다 | 짧다 |
| 설명 메모(주석) | `<!-- 이렇게 -->` 달 수 있다 | 달 수 없다 |
| 브라우저가 오류를 잡아 주나 | 잡아 준다 | 잡아 주지 않는다 |
| 주로 쓰이는 곳 | 공공·금융·문서 내부 | 웹·앱·AI |

주의할 규칙이 하나 있습니다. 꺾쇠괄호와 `&` 기호는 이름표를 여닫는 데 쓰는 글자라 내용에 그냥 넣을 수 없습니다. 회사 이름이 `한빛 & 새빛`이라면 `&`를 그대로 적는 순간 파일 전체가 오류가 납니다. 실제로 넣어 보니 "형식에 맞지 않는 문서"라며 읽기를 거부했습니다. 이럴 때는 `&amp;`라고 적어야 합니다. 회사 이름에 `&`가 든 곳이라면 실무에서 종종 겪는 문제입니다.

[[TIP("손으로 해보기 · 이미 갖고 있는 XML 열어보기")]]
1. **메모장에 위 예시를 적고** `직원.xml`로 저장한 뒤 브라우저로 끌어다 놓습니다. 나무 모양으로 펼쳐집니다.
2. **일부러 깨뜨립니다.** `</부서>`를 `</직원>`으로 바꿔 저장하고 새로고침하세요. 오류가 몇 번째 줄 몇 번째 칸인지 알려 줍니다.
3. **진짜 문서를 열어 봅니다.** 1장과 2장에서 압축을 풀어 두었던 폴더가 아직 있다면, 그 안의 `section0.xml`이나 `word/document.xml`을 브라우저로 끌어다 놓으세요. 여러분이 쓴 문서가 이름표로 감싸인 모습이 그대로 보입니다.
4. **세금계산서가 있다면** 그것도 열어 보세요. 공급자와 공급받는자, 품목과 금액이 각각 이름표를 달고 앉아 있습니다.
[[/TIP]]

## 왜 아직도 XML인가

JSON이 더 짧고 간편한데 왜 XML이 남아 있을까요. 이유를 알면 이 형식을 어디서 만나게 될지도 함께 보입니다.

첫째, **공공과 금융 분야는 한 번 정한 규격을 오래 씁니다.** 전자세금계산서 표준은 2009년에 만들어져 2011년부터 전면 시행됐습니다. 수많은 회사의 시스템이 그 규격에 맞춰 돌아가고 있으니 유행이 바뀌었다고 갈아엎을 수가 없습니다. 정부가 제공하는 공공데이터 통로에서도 XML을 함께 내주는 곳이 많습니다.

둘째, **문서를 담기에는 XML이 더 낫습니다.** 이 책 1부에서 확인한 대로 한글·워드·엑셀·파워포인트가 전부 속에 XML을 품고 있습니다. 문장 중간의 한 단어만 굵게 만드는 것처럼 글 안에 표시를 끼워 넣는 일은 이름표로 감싸는 방식이 자연스럽습니다.

셋째, **규격을 강제할 수 있습니다.** XML에는 "이 문서에는 반드시 공급자 사업자번호가 있어야 하고 열 자리여야 한다"는 식의 규칙을 따로 정해 두고 검사하는 장치가 있습니다. 세금계산서처럼 틀리면 안 되는 문서에는 이 성질이 중요합니다.

## 그래서 무엇을 자동화하나

XML을 만나는 자리는 대개 정해져 있고, 그래서 자동화의 모양도 분명합니다.

**회계팀의 세금계산서 정리입니다.** 매달 거래처에서 XML 파일이 수십 개에서 수백 개씩 들어옵니다. 지금은 하나씩 열어 공급자와 금액을 확인하고 엑셀에 옮겨 적거나, 회계 프로그램에 하나씩 올립니다. 그런데 이 파일들은 모두 같은 규격이라 이름표 위치가 똑같습니다. 폴더에 모아 두고 필요한 이름표만 뽑아 표로 만드는 일은 한 번 만들어 두면 매달 그대로 씁니다. 부가세 신고 기간의 반복 작업이 여기서 크게 줄어듭니다.

**기획팀의 공공데이터 수집입니다.** 인구 통계, 상권 정보, 날씨 같은 자료를 공공데이터 통로에서 받아 오면 XML로 오는 경우가 많습니다. 화면에서 하나씩 검색해 옮겨 적는 대신, 필요한 항목만 뽑아 엑셀로 펴는 일을 맡길 수 있습니다.

**총무팀의 문서 일괄 점검입니다.** 1부에서 배운 것과 이 장이 만나는 자리입니다. 폴더에 쌓인 워드 문서 수백 개에서 특정 문구가 든 파일만 찾아야 한다고 해 봅시다. 파일을 하나씩 열어 확인하는 대신, 각 문서의 속에 든 XML에서 글자만 뽑아 훑으면 됩니다. 옛 사명이 남아 있는 문서를 찾아내거나, 계약서에서 특정 조항이 빠진 것을 골라내는 일이 여기 해당합니다.

사람과 AI의 몫은 여기서도 같습니다. 어떤 이름표가 우리에게 필요한 정보인지 정하는 일, 그리고 뽑아낸 숫자가 상식에 맞는지 판단하는 일은 사람이 합니다. 파일을 열고 이름표를 찾아 값을 꺼내 표로 정리하는 일은 AI에게 넘깁니다.

## AI에게 시키는 법

XML은 이름표 이름만 알면 지시가 아주 간단해집니다. 그런데 처음 받은 파일은 이름표를 모르지요. 그럴 때는 파일을 그대로 올리고 이렇게 물으면 됩니다.

```text
이 XML 파일의 구조를 알려 줘.
· 어떤 이름표들이 있고 각각 무슨 뜻으로 보이는지
· 그중 금액, 날짜, 사업자번호에 해당하는 이름표는 무엇인지
· 같은 이름표가 여러 번 반복되는 곳이 있는지 (품목처럼)
표로 정리해 줘.
```

구조를 알고 나면 뽑아내는 도구를 만들라고 하면 됩니다.

```text
브라우저에서만 도는 HTML 파일 하나를 만들어 줘. 서버는 쓰지 마.

할 일: 세금계산서 XML 파일 여러 개를 한꺼번에 올리면
한 건에 한 줄씩 표로 만들어 CSV로 내려받게 해 줘.

반드시 지킬 규칙:
· 뽑을 항목은 작성일자, 공급자 상호, 공급자 사업자번호,
  공급받는자 상호, 공급가액, 세액, 합계금액이야.
· 사업자번호는 글자로 다뤄. 앞자리 0이 사라지면 안 돼.
· 품목이 여러 개면 합계 기준으로 한 줄만 만들고,
  품목 수를 따로 한 칸에 적어 줘.
· 이름표를 못 찾은 파일은 건너뛰지 말고 목록으로 보여 줘.
· CSV는 UTF-8 BOM으로 저장해.
· 올린 파일 수와 만들어진 줄 수를 나란히 보여 줘.
```

네 번째 조건이 실무에서 특히 중요합니다. 거래처마다 쓰는 발행 시스템이 달라 이름표가 조금씩 다를 수 있는데, 그런 파일을 조용히 건너뛰면 몇 건이 빠진 채로 집계가 끝나 버립니다. **실패한 것을 실패했다고 알려 달라는 조건**은 어떤 자동화에서도 넣어 두시는 편이 좋습니다.

한계도 적어 두겠습니다. XML은 같은 내용을 담아도 JSON보다 파일이 커집니다. 이름표를 두 번씩 적기 때문입니다. 그리고 실제 업무에서 받는 XML은 예시처럼 깔끔하지 않습니다. 이름표 앞에 `<tax:` 같은 접두사가 붙어 있거나, 규격 주소가 길게 적혀 있어 처음 보면 겁이 납니다. 그런 것들은 대부분 "어느 규격을 따르는지" 밝히는 표시일 뿐이니, 무시하고 안쪽의 이름표만 보시면 됩니다.

마지막으로 한 가지만 당부드립니다. 세금계산서 XML에는 사업자번호와 거래 내역이 들어 있습니다. 개인정보이자 영업 정보입니다. 인터넷의 무료 변환 사이트에 올려 확인하는 일은 피하시고, 내 컴퓨터 안에서 처리하는 방식을 쓰십시오. 이 책이 계속 브라우저 안에서만 도는 도구를 만들라고 지시문에 적어 온 이유가 여기에 있습니다.

## 이름표의 계보

여기까지 오면 확장자를 보는 눈이 꽤 달라져 있을 겁니다. 한글 문서도, 오피스 문서도, 전자책도, 그림도, 세금계산서도 결국 이름표를 붙인 글자였습니다. 표로 적은 것이 CSV였고, 중괄호로 적은 것이 JSON이었으며, 꺾쇠로 감싼 것이 XML이었습니다. 담는 방식이 다를 뿐 하는 일은 같습니다.

그런데 이 방식들이 불편했던 사람들이 있습니다. 꺾쇠는 같은 이름을 두 번 적어야 해서 길고, 중괄호와 따옴표는 손으로 타이핑하기 번거로우며, JSON에는 설명 메모조차 달 수 없습니다. 그래서 괄호를 전부 걷어내고 들여쓰기만으로 구조를 표현하는 형식이 나왔습니다. 다만 괄호를 없앤 데에는 대가가 따랐습니다.
